# AGENTS.md

This file provides guidance to Ai Agents when working with code in this repository.

## Primary goals and decision rules

The target service is **threadquirk.lv**. Every product, design, content, technical, and infrastructure decision must support these two primary goals:

1. **Quality prints and fast discovery.** Build a high-quality service with high-quality prints, where visitors quickly find what they need. Prioritize artwork quality, relevant catalog results, clear navigation, useful search and filters, and fast, accessible pages.
2. **Organic search visibility.** Make threadquirk.lv popular and easy to discover through Google, Bing, and other search engines. Maximize useful search visibility and organic traffic through helpful content, discoverable catalog pages, and sound technical SEO, while preserving visitor experience and print quality.

**Target audience:** international, English-speaking visitors. Prioritize English catalog search, content, and search intent across international markets; do not assume Latvia-only targeting from the `.lv` domain. Evaluate additional languages or country-specific pages only when evidence supports their benefit to these goals.

Before proposing or implementing a change, explain which goal it serves and how its benefit can be verified. Evaluate tradeoffs against both goals; organic traffic must not come at the expense of catalog quality or visitors' ability to find relevant prints.

**Cost discipline:** maximize the use of free services, existing resources, and simple self-hosted or in-house solutions. Do not optimize for higher spending or add paid dependencies by default. When a paid option is justified, compare it with viable free or self-hosted alternatives and explain its concrete benefit, recurring cost, usage limits, and maintenance burden before recommending it. Choose the simplest adequate solution, accounting for both service fees and upkeep.

These goals guide this deployment; keep the underlying white-label engine configurable rather than hardcoding the domain or brand into reusable code.

## What this is

Design Studio is a self-hostable, white-label print-on-demand storefront (Next.js 16 App Router, React 19, Tailwind 3). It mirrors an artist's Redbubble shop into a searchable catalog and sends buyers to the marketplace to purchase — there is no checkout and no admin UI. See `PRODUCT.md` (users, purpose) and `DESIGN.md` (visual system) before UI work; `docs/` holds deeper Russian-language docs (architecture, database, sync, deployment) that may lag the code — trust the source when they disagree.

## Architecture

**Data access goes only through `utils/database.ts`.** It is a dual-provider facade selected by `DATABASE_PROVIDER` (`supabase` default, or `mysql`); clients are created lazily (`getSupabase()`, `getMySQLPool()` — the MySQL pool is cached on `globalThis` to survive HMR). Every exported query (`loadSiteConfig`/`getSiteConfig`, `fetchDesigns`, `getDesignById`, `getDesignBySlug`, `fetchRandomDesigns`, `fetchCollections`) branches on the provider, so any new query must be implemented for **both** backends and return the same normalized `Design` shape (`types/design.ts`). `loadSiteConfig` keeps a last-known-good config in memory, so a transient DB outage serves the previous config instead of a 500. The sync pipeline writes the sentinel `no_collection` into `designs.collection` for uncollected designs; every read normalizes it back to `""` (`normalizeCollection`) so the UI never sees it. SQL schema and stored functions (`get_random_designs`) live in `init/` for both Postgres and MySQL — keep them in sync, including `init/migrations/001_collections_*.sql`, which upgrades installs that predate the collections tables, and `init/migrations/002_design_slugs_*.sql`, which adds the nullable unique `designs.slug` column.

**Configuration is layered:** `config/config.json` (defaults) → rows of the `studio` table (`key`/`value`, dot-notation keys like `social.twitter` or `representation.redbubbleShopUrl` are expanded into nested objects by `mapDataToConfig` in `lib/config.ts`, which deep-clones the base and blocks prototype-pollution keys) → env vars for secrets. `app/layout.tsx` calls `getSiteConfig()` on the server and passes the result to client components through `ConfigContext` in `app/wrapper.tsx`; client components read config via `useContext(ConfigContext)`. The `SiteConfig` type lives in `lib/store.ts` (which also has a Zustand store seeded from the JSON defaults). `getSiteConfig` is cached (React `cache` wrapping `unstable_cache`, tag `site-config`, 5-min TTL, invalidated by `POST /api/revalidate/config` — authenticated with `SYNC_SECRET` through the shared `authorizeSyncRequest` helper); code that runs outside the Next.js runtime (CLI scripts, tests) must import the uncached `loadSiteConfig` instead.

**Sync pipeline** (`lib/sync/redbubble.ts`): scrapes the public Redbubble shop by parsing the page's `__NEXT_DATA__` JSON (`parseShopNextData`) with either Playwright (stealth Chromium, persisted storage state for Cloudflare) or a plain Cheerio `fetch` (falling back to anchor-tag scanning if `__NEXT_DATA__` is missing), paced by `RequestPacer` (min interval + jitter), then upserts into `designs` — including each design's Classic T-Shirt mockup URL in `props.mockup_tshirt` (surfaced as `mockupUrl` by the public API DTO). A `slug` is assigned once, on insert only, and never rewritten on update, so a design's URL stays stable. Redbubble's `artistInfo.collections` are treated as the source of truth for the many-to-many `collections`/`design_collections` tables: after the listing pages, the pipeline crawls each `?collections=<id>` filtered page to build design↔collection membership, then upserts `collections` and rewrites each synced design's `design_collections` links (only when the crawl fully succeeded — `collectionsComplete`). Note it always writes to **Supabase** (`writeDesignsToSupabase` / `syncRedbubbleToSupabase`) regardless of `DATABASE_PROVIDER`. Entry points: `scripts/sync-redbubble.ts` (CLI, `--target=db|json|both`) and `POST /api/sync/redbubble` (auth via `authorizeSyncRequest` in `lib/sync-auth.ts`: `SYNC_SECRET` sent as `Authorization: Bearer` or `x-sync-secret`, constant-time compared — unconfigured secret returns 500, wrong secret 401; in-process lock returns 409 on concurrent runs; the route refuses to run when `DATABASE_PROVIDER=mysql` since the sync writes to Supabase only). Tuning env vars are listed in `.env.example`. Playwright sessions don't persist on serverless — run the sync on a machine/VM when Cloudflare challenges appear (first run with `SYNC_PLAYWRIGHT_HEADLESS=false`).

**Backgrounds:** Redbubble fills transparent artwork areas with whatever color is baked into the requested image variant; arbitrary hex is rejected — only a signed color token (`<hex6>[~<hex6>]:<hash10>`, e.g. the artist's own Classic T-Shirt mockup color already carried in `props.mockup_tshirt`, or one of two known site-wide presets) works, via `lib/background.ts`. `POST /api/designs/background` (auth via `authorizeSyncRequest`, same as the sync route) takes `{ color: "auto"|"white"|"black"|"<token>", ids?: string[], all?: boolean, dryRun?: boolean }`, resolves and writes `designs.externalImageUrl`/`backgroundColor` through `setDesignBackgrounds`/`updateDesignBackground`, and revalidates the site layout on a real (non-dry) update; the CLI equivalent is `scripts/set-background.ts` (`npm run designs:background[:dry]`). New designs synced going forward get their artist mockup color baked in immediately (`lib/sync/redbubble.ts`); existing rows are unchanged until backfilled via the endpoint/CLI. The public API also accepts a `bg` query param (same values) on `/api/v1/prints`, `/api/v1/prints/random`, and `/api/v1/prints/{id}` to override `imageUrl`/`backgroundColor` on the fly per request (400 on an invalid value); omitting it leaves responses unchanged.
**TeePublic link sync** (`lib/sync/teepublic.ts`, CLI `scripts/sync-teepublic.ts`): the same artist also sells the same designs on TeePublic. It never creates designs — it only matches each scraped TeePublic design to an existing `designs` row by title (exact normalized-title match first, then fuzzy Dice-coefficient similarity ≥ `--threshold`, default 0.8, with a confidence margin over the runner-up to avoid guessing between near-ties). Only **exact** title matches are written to `props.teepublicLink` (canonical design URL) and `props.teepublicId`, preserving every other `props` key (e.g. `mockup_tshirt`); fuzzy matches are never auto-applied (a high Dice score can still be a false positive, e.g. "Retro New York City Sunset" vs "Retro New York State Sunset") and are instead listed in the CLI's `fuzzy` report array for a human to review and link manually. `splitMatches` in `lib/sync/teepublic.ts` does this exact/fuzzy split. Always writes to Supabase regardless of `DATABASE_PROVIDER`, same as the Redbubble sync. Page count is capped independently via `TEEPUBLIC_MAX_PAGES` (default 20) — deliberately not `SYNC_MAX_PAGES`, which is Redbubble's own cap and would otherwise silently truncate the TeePublic scrape too. Two scrape sources, chosen with `--source=feed|browser` (env `TEEPUBLIC_SOURCE`, default `feed`): the default `feed` source fetches TeePublic's public `/user/<name>/feed?page=N` listing (same design tiles as the store page) through the system `curl` binary with an honest, self-identifying User-Agent — plain Node `fetch` is blocked outright by Cloudflare's TLS fingerprinting regardless of headers, but `curl` isn't, and this path never launches a browser. `--source=browser` keeps the original Playwright path (`createPlaywrightSession`, reused from `lib/sync/redbubble.ts`) for when `/feed` itself is unavailable; page 1 there is a Cloudflare Turnstile checkbox that only a human can clear (`SYNC_PLAYWRIGHT_HEADLESS=false`, then reuse the saved storage state headless) — the code only navigates and passively waits for it, never automates the click.

**Public API:** `/api/v1/prints` (paginated, `page`/`limit`/`q`/`collection`/`keywords`), `/api/v1/prints/random` (`limit`/`collection`/`keywords`), `/api/v1/prints/[id]`, and `/api/v1/collections` are unauthenticated, read-only GET endpoints meant for other sites to embed prints as referral/ad blocks; each item is normalized to the `PublicPrint` DTO (`lib/public-api.ts`, built from `Design` via `toPublicPrint`) with a direct `link` to the Redbubble listing. Cross-origin access is controlled by the `PRINTS_API_ALLOWED_ORIGINS` env var (comma-separated origins, or `*`; unset/empty defaults to `*`, i.e. any origin), applied via `corsHeaders`/`jsonResponse`/`optionsResponse` in `lib/public-api.ts`; every route also exports `OPTIONS` for CORS preflight. Successful responses are cached with `Cache-Control: public, s-maxage=300, stale-while-revalidate=600` (the random endpoint uses `no-store` so it doesn't get frozen by the CDN); errors always use `no-store`. Separately, `POST /api/contact` (unauthenticated) validates `{name, email, message}` and relays it to the `CONTACT_WEBHOOK_URL` webhook; with that var unset it answers 501 `not_configured` so the contact form can say sending isn't set up instead of pretending.

**Affiliate links:** the database stores only canonical marketplace URLs (`designs.externalLink`, `props.teepublicLink`); affiliate tracking is applied at render/API time through `lib/affiliate.ts` — `applyRedbubbleAffiliate` wraps a URL in the Impact deep-link template from the `affiliate.redbubbleTemplate` studio row (copied verbatim from Impact's link builder, `{url}` placeholder), `applyTeepublicReferral` appends `?ref_id=` from `affiliate.teepublicReferralId`. Both are no-ops while the config values are empty, and linking codes must never be hand-mutated anywhere else (the affiliate ToS only allows codes obtained from the affiliate interface). Call sites: the design detail page, `ShopLinks` on the contact page (wrapped server-side in the page), and `toPublicPrint` in `lib/public-api.ts` (routes pass `getAffiliateOptions(getSiteConfig())`). Outbound buy anchors use `rel="sponsored noopener noreferrer"`, and pages showing buy links carry an affiliate disclosure next to the CTA plus `/disclosure` (linked from the footer) — the marketplaces' affiliate terms (Redbubble's runs on Impact; see the FTC disclosure section of its ToS) require a visible disclosure wherever affiliate links appear, so keep it there when adding new buy-link surfaces. Marketplace logos must not be recreated in the UI — Redbubble's ToS only allows logos provided in the Impact platform.

**Rendering:** pages are Server Components by default and query the DB directly through the facade; `"use client"` only where hooks/browser APIs are needed (search bar, cookie banner — `localStorage` in an effect, react-slick carousel with pause controls and `prefers-reduced-motion` support, contact form, header/footer, social/shop links). Google Analytics loads via `@next/third-parties` when `analytics.google` is configured. The design detail page lives at `app/designs/[slug]` and resolves either a slug or a legacy UUID, `permanentRedirect`-ing (308) from `/designs/<uuid>` to `/designs/<slug>` when the design has one; links are built with `designPath` (`lib/slug.ts`), which falls back to the UUID when no slug is set. SEO pieces: per-page `metadata`/`generateMetadata`, `app/sitemap.ts`, `app/robots.ts`, `app/components/JsonLd.tsx`. Remote images are allowed only from `*.redbubble.com`, `*.redbubble.net`, `*.placeholder.com` (`next.config.mjs`), which also sets global security headers.

**Collection discovery and curation:** `studio.collectionPages` (or optional `collectionPages` in the JSON defaults) holds an array or JSON-encoded array of `{collection, title, description, intro}` profiles. The catalog uses these for prepared theme pages, falls back to the collection's database description for other themes, and keeps searches and empty/unknown collection results `noindex`. `fetchFeaturedCollections` promotes only configured, existing, nonempty themes in home/catalog links and `/sitemap.xml`. Keep existing `/designs?collection=...` URLs and page-specific canonicals. Related designs use all `design_collections` memberships, excluding the current design, with a legacy single-collection fallback. Reviewed local memberships are additive: `addCuratedCollections` stores titles in `props.curatedCollections`, preserves other props and existing primary labels, and upserts join rows. Redbubble sync unions these reviewed titles with marketplace memberships for collections present in its complete crawl; if Redbubble has no primary label, the first valid curated title supplies it. Use `scripts/curate-collections.ts --plan=<reviewed.json> --dry-run` to validate a plan and `--apply` to write it after a timestamped backup in `.cache/`; source marketplace membership facts remain authoritative for the non-curated part.

Collection profiles may also provide an optional short `heading`, used for the visible H1 and navigation labels while `title` remains the metadata title. On a selected collection page, neighboring theme links follow the results/pagination so they do not push mobile prints below the first screen. After updating `collectionPages`, use the authenticated config revalidation endpoint or allow the existing five-minute cache TTL to refresh; CLI scripts use `loadSiteConfig` for uncached reads.

## Styling / design system

- Colors and radii are HSL CSS variables in `app/globals.css` (`:root`), mapped to Tailwind semantic names in `tailwind.config.ts` (`bg-primary`, `text-accent`, `border-input`, …). Use those tokens, never literal color values — deployments re-skin by overriding the variables or via the `themeLink` config (validated by `isAllowedThemeUrl` in `app/layout.tsx`).
- UI primitives are shadcn/ui ("new-york", `components/ui/`); site-specific components live in `app/components/`. Use `cn()` from `lib/utils.ts` for class merging.
- `DESIGN.md` defines the palette names (Loom Ink, Indigo Thread as the single interactive hue, etc.), typography scale, and rules — follow it for any visual change.
