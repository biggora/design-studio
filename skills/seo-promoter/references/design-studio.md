# SEO-правки и внедрение в design-studio

Актуальная архитектура ниже сверена с кодом 6 ноября 2026. Перед изменением проверь её в текущей ветке; имена файлов — точки поиска, не неизменяемый API.

## Область работы

Публичный сайт — репозиторий design-studio (в этой среде `E:/Projects/ai-automations/saas/print-on-demand/design-studio`), а pod-studio — приложение создания принтов. Публикация SEO-текста на сайте не требует менять исходный рисунок, marketplace listing или запускать генерацию новых принтов.

Сверь AGENTS.md, рабочее дерево и существующие изменения пользователя. Для UI прочитай PRODUCT.md / DESIGN.md. Текущий продукт — конфигурируемый storefront: покупка завершается на маркетплейсе. Англоязычную международную аудиторию нельзя ограничивать Латвией только из-за `.lv`.

## Подготовить изменения

Для каждого URL составь точное «сейчас → предлагается» и цель изменения:

- **Title:** ясно назови товар/намерение и отличительный принт. Слоган можно сократить в title, оставив его полным в H1/описании.
- **H1:** один понятный главный заголовок, соответствующий реальному товару.
- **Meta description:** самостоятельное описание без повторного префикса названия, с конкретным сюжетом и следующим действием. Google может выбрать другой snippet; редакционная длина не является жёстким лимитом показа.
- **Видимый текст:** сначала кому подходит и что это за товар, затем достоверные детали рисунка/слогана. Формулировка «quilting tee» допустима как синоним, даже если у неё нет отдельного измеренного объёма.
- **Alt:** описывает фактически показанный мокап, читаемый слоган и важный рисунок. Не превращай его в список поисковых фраз или обещание всех вариантов цвета.
- **Ссылки:** постоянные тематические переходы с понятными anchor text. Существование random related rail не гарантирует связь двух подходящих принтов. Не вытесняй карточки каталога большим SEO-блоком на мобильном экране.
- **Техника:** исправляй подтверждённые проблемы HTTP, canonical, noindex/robots, sitemap и доступности изображений, а не добавляй работу ради полного чек-листа.

Не делай одинаковые страницы под перестановки/написания ключей. Сохраняй уже существующие URL, если нет отдельной обоснованной задачи миграции. Создавай новую подборку только при полезном ассортименте и подходящем намерении. Создание публичной SEO-подборки не даёт разрешения создавать дополнительные коллекции в студии/на маркетплейсах; в исходной сессии действовал лимит 30, актуальный лимит уточняй по проектной памяти.

Для структурированных данных проверь текущую реализацию и правила Google. Не придумывай цены, наличие, отзывы, материалы, бесплатную доставку или возвраты. Внешняя ссылка покупки сама по себе не делает storefront подходящим для merchant listings: Google отдельно требует возможность купить на странице. Валидатор схемы не гарантирует право на конкретный вид результата. Не сноси существующую проверенную разметку в обычном текстовом SEO-задании без выяснения причин.

## Использовать существующие настройки

| Часть | Точки в коде |
|---|---|
| SEO-профили дизайнов | `lib/design-pages.ts`, `SiteConfig.designPages` в `lib/store.ts` |
| Metadata, H1, текст, alt, related | `app/designs/[slug]/page.tsx` |
| Подарочные страницы и ссылки | `lib/gifts.ts`, `app/gifts/[slug]/page.tsx` |
| Активные назначения ссылок | `lib/design-links.ts`, `app/components/CuratedDesignLinks.tsx` |
| Валидация/запись текстовых настроек | `lib/seo-copy.ts`, `scripts/apply-seo-copy.ts` |
| Единственный доступ к данным | `utils/database.ts`, оба поддерживаемых backend |
| Коллекции, если они входят в поручение | `scripts/curate-collections.ts`, существующая additive curation |

На текущую дату `studio.designPages` принимает массив или JSON-текст. Элемент:

```json
{
  "slug": "existing-design-slug",
  "title": "Quilter T-Shirt – Distinctive Slogan",
  "heading": "Quilter T-Shirt: The Complete Slogan",
  "description": "Independent factual meta description.",
  "intro": "Useful visible product introduction.",
  "imageAlt": "Description of the actual T-shirt mockup",
  "buyingInfo": "Optional factual store-selection guidance.",
  "related": {
    "heading": "More quilting T-shirts",
    "links": [{"slug": "another-existing-design", "label": "Descriptive quilter T-shirt name"}]
  }
}
```

`slug`, `title`, `heading`, `description`, `intro`, `imageAlt` обязательны в текущем parser. `buyingInfo` и `related` необязательны. Title хранится **без бренда**, renderer добавляет `| <config.name>`; старые страницы без профиля сохраняют прежний fallback. Не переименовывай marketplace-backed `design.title`, чтобы задать независимые title/H1/meta. Artwork identity и замороженные OG/Pinterest assignments имеют собственные назначения; новый SEO-заголовок не требует их пересоздания.

`giftPages[].designLinks` использует `{heading, intro?, links:[{slug,label}]}`. Сейчас блок выводится после сетки/пагинации перед FAQ, только на первой нефильтрованной странице. Назначения разрешаются через активный каталог, отсутствующие/скрытые/повторные/self ссылки не отображаются. Текст ссылки не должен обещать другой товар.

## Применить настройки без потери соседних данных

1. Сначала прочитай текущую конфигурацию нужного окружения через facade. Проверь домен **и назначение подключения**: одного одинакового названия сайта недостаточно, чтобы отличить локальную копию от production. Не печатай секреты.
2. Сохрани текущие затрагиваемые ключи. Собери новый план из свежих значений, меняя только нужные профили. **`giftPages`, `designPages`, `collectionPages` в существующем copy writer заменяют целые массивы**, а не частично дополняют их. Поэтому план с одной gift-страницей может удалить остальные. Сохраняй чужие профили и не применяй исторический full-array план вслепую.
3. Проверь diff и dry-run:

   ```powershell
   npx tsx scripts/apply-seo-copy.ts --plan=<reviewed-plan.json> --dry-run
   ```

4. Непосредственно перед записью сравни исходные затрагиваемые значения со свежими. Если их изменил кто-то ещё, пересобери план и проверь diff. При разрешённом внедрении используй `--apply`; существующий инструмент создаёт `.cache/seo-copy-<timestamp>.json`.
5. Прочитай данные обратно и сравни **значения**, а не только число элементов. Убедись, что соседние профили сохранились. После timeout записи сначала проверь фактическое состояние; повторяй только явно не выполненную операцию. Если определить его нельзя, останови зависимые записи и назови неопределённость.

Не добавляй схему БД, новый endpoint или автоматизацию, если существующей конфигурации достаточно. Если необходима запись данных, она проходит через `utils/database.ts`, с поддержкой обоих backend согласно AGENTS.md.

## Проверить и опубликовать в разрешённом объёме

Обычная конфигурационная правка не требует нового набора тестов, повторяющих текст. Если меняешь renderer/parser, проверь значимое поведение: fallback, независимость identity/canonical, сохранность соседних профилей, исключение недоступных ссылок. Запусти подходящие существующие тесты, TypeScript/ESLint и сборку соразмерно изменению.

Если общий suite падает вне scope, установи, воспроизводится ли ошибка на исходной версии. Не объявляй suite зелёным и не меняй посторонний механизм ради SEO-правки. Не отправляй чужие изменения пользователя вместе со своим коммитом.

При разрешённой публикации используй обычный проектный путь. В исходной сессии push в `main` запускал Vercel; это нужно подтвердить для текущей ветки/проекта. Дождись статуса именно нужного SHA, затем проверь публичный HTML и отображение изменённых страниц, ссылки и одну незатронутую страницу. Не заходи в панель провайдера и не создавай новые доступы, если штатный путь достаточен. Не запускай повторные деплои, пока прежний результат не выяснен.

## Если deploy успешен, но тексты старые

Разделяй слои: данные БД, `getSiteConfig` Data Cache, ISR/CDN страницы, браузер и отдельный сохранённый crawl Google. `x-vercel-cache: MISS` страницы не доказывает свежесть вложенного config Data Cache.

Сначала сравни сохранённые значения, фактически отданные title/H1 и код опубликованного SHA. Затем используй имеющийся авторизованный `POST /api/revalidate/config`, если он настроен и применим; `revalidateTag(..., "max")` может сначала вернуть stale-ответ и обновить его в фоне.

Если endpoint не настроен, зафиксируй ошибку и не меняй секреты/доступы попутно. Оцени существующий TTL и возможный узкий исправляющий rollout. В этой сессии новый schema key `editorial-pages-v1` исключил повторное использование pre-profile config snapshot при добавлении полей. **Не копируй это как обязательное действие при каждой правке текста**: бессмысленные cache-bump/empty commits маскируют причину и запускают лишние сборки. Если немедленное безопасное обновление недоступно, сообщи точный статус/срок вместо ложного «уже опубликовано».

## Проверка HTML скриптом

Из корня design-studio, с установленными зависимостями проекта (Node с `fetch` и `cheerio`):

```powershell
node --use-system-ca skills/seo-promoter/scripts/audit-pages.mjs --manifest=.cache/seo/check.json --output=.cache/seo/http-result.json
```

Manifest содержит `pages`. Для исходного аудита достаточно `url`; для проверки правок добавь `expect`:

```json
{
  "pages": [
    {
      "url": "https://threadquirk.lv/designs/existing-design-slug",
      "expect": {
        "title": "Reviewed Title | ThreadQuirk",
        "h1": "Reviewed visible heading",
        "canonical": "https://threadquirk.lv/designs/existing-design-slug",
        "meta": {"description": "Reviewed description", "og:image": "https://images.example.test/frozen.jpg"},
        "imageAlt": "Reviewed mockup alt",
        "textIncludes": ["A factual sentence that must be visible."],
        "indexable": true,
        "links": [{"href": "/designs/another-existing-design", "text": "Reviewed anchor", "sectionHeading": "More quilting T-shirts"}]
      }
    }
  ]
}
```

Это пример формата; замени адреса/ожидания данными конкретного задания. Скрипт проверяет HTTP 200, собирает title, meta, canonical, H1, заголовки, изображения, ссылки и типы JSON-LD; опциональные ожидания сравнивает с исходным HTML. Для `indexable: true` он проверяет отсутствие noindex в meta/X-Robots-Tag — это не доказательство попадания в индекс или разрешения robots.txt.

Коды выхода: `0` — HTTP/ожидания прошли; `1` — ошибка загрузки или несоответствие; `2` — некорректные аргументы/manifest. JSON с результатами страниц пишется и при несоответствиях. Сетевые запросы только GET, без credentials и автоматических повторов. Запускай для выбранных разрешённых страниц, не для скрытых административных URL.

Скрипт не выполняет JS, не проверяет все ссылки переходом и не заменяет браузер, GSC URL Inspection, проверку robots/sitemap, layout, спроса или юридическую оценку разметки. Для JS-only содержимого дополнительно используй разрешённый браузер.

Источники: [title links](https://developers.google.com/search/docs/appearance/title-link), [snippets](https://developers.google.com/search/docs/appearance/snippet), [Google Images](https://developers.google.com/search/docs/appearance/google-images), [merchant listing eligibility](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing#guidelines).
