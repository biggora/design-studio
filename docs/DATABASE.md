# Design Studio Database Specification

## 1. Data Storage Architecture Overview

The **Design Studio** project supports two relational database management systems:

1. **PostgreSQL / Supabase** — the default cloud database with a built-in REST API, Row Level Security (RLS), and automatic UUID generation.
2. **MySQL (v8+)** — a traditional relational database connected through a `mysql2/promise` connection pool.

Switching between the databases is controlled by the `DATABASE_PROVIDER` environment variable: `DATABASE_PROVIDER=supabase` (default when unset) or `DATABASE_PROVIDER=mysql`. The value is validated in `utils/database.ts` (`getProvider()`); any other value throws `Unsupported DATABASE_PROVIDER: <value>` at request time.

## 2. Table Structure

The catalog database consists of two main tables:

- `studio` — a key/value table for dynamic project settings.
- `designs` — the catalog of artwork, product metadata, tags, and links to external marketplaces.

### 2.1 Table `studio` (Site Configuration)

Stores overrides of the global configuration.

#### PostgreSQL schema (`init/postgres_tables.sql`)
```sql
CREATE TABLE public.studio (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    key CHARACTER VARYING NULL,
    value TEXT NULL,
    createdat TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
    CONSTRAINT studio_pkey PRIMARY KEY (id)
) TABLESPACE pg_default;
```

#### MySQL schema (`init/mysql_tables.sql`)
```sql
CREATE TABLE studio (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  `key` VARCHAR(255),
  value TEXT,
  createdat TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

#### Field reference for `studio`
| Field | PostgreSQL type | MySQL type | Nullable | Description / Example |
|---|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT` | `BIGINT AUTO_INCREMENT` | NO | Numeric primary key of the row. |
| `key` | `VARCHAR` | `VARCHAR(255)` | YES | Configuration key name. Supports dot notation (`social.twitter`, `representation.redbubbleShopUrl`). |
| `value` | `TEXT` | `TEXT` | YES | Parameter value (string, URL, analytics ID). |
| `createdat` | `TIMESTAMP WITH TIME ZONE` | `TIMESTAMP` | NO | Row creation timestamp (defaults to the current time). |

### 2.2 Table `designs` (Design Catalog)

Stores design cards, links to the original images, categories, collections, and synchronization attributes.

#### PostgreSQL schema (`init/postgres_tables.sql`)
```sql
CREATE TABLE public.designs (
    id UUID NOT NULL DEFAULT gen_random_uuid(),
    "externalId" BIGINT NOT NULL,
    title CHARACTER VARYING NOT NULL,
    description TEXT NOT NULL,
    keywords TEXT NOT NULL,
    "imageName" CHARACTER VARYING NULL,
    "externalImageUrl" TEXT NULL,
    "externalLink" TEXT NULL,
    category CHARACTER VARYING NULL DEFAULT 'no_category'::character varying,
    collection CHARACTER VARYING NULL DEFAULT 'no_collection'::character varying,
    "backgroundColor" CHARACTER VARYING NOT NULL DEFAULT '#FFFFFF'::character varying,
    "backgroundColors" TEXT NULL,
    shared BOOLEAN NULL DEFAULT false,
    props JSON NULL,
    "createdAt" TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
    "updatedAt" TIMESTAMP WITHOUT TIME ZONE NULL,
    CONSTRAINT designs_pkey PRIMARY KEY (id),
    CONSTRAINT designs_externalid_key UNIQUE ("externalId"),
    CONSTRAINT designs_title_key UNIQUE (title)
) TABLESPACE pg_default;
```

#### MySQL schema (`init/mysql_tables.sql`)
```sql
CREATE TABLE designs (
  id CHAR(36) NOT NULL DEFAULT (UUID()),
  `externalId` BIGINT NOT NULL,
  title VARCHAR(255) NOT NULL,
  description TEXT NOT NULL,
  keywords TEXT NOT NULL,
  `imageName` VARCHAR(255),
  `externalImageUrl` TEXT,
  `externalLink` TEXT,
  category VARCHAR(255) DEFAULT 'no_category',
  collection VARCHAR(255) DEFAULT 'no_collection',
  `backgroundColor` VARCHAR(255) NOT NULL DEFAULT '#FFFFFF',
  `backgroundColors` TEXT,
  shared BOOLEAN DEFAULT FALSE,
  props JSON,
  `createdAt` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updatedAt` TIMESTAMP NULL,
  PRIMARY KEY (id),
  UNIQUE KEY designs_externalid_key(`externalId`),
  UNIQUE KEY designs_title_key(title)
);
```

#### Field reference for `designs`
| Field | PostgreSQL type | MySQL type | Constraints | Purpose |
|---|---|---|---|---|
| `id` | `UUID` | `CHAR(36)` | PRIMARY KEY, DEFAULT UUID | Internal unique record identifier. |
| `externalId` | `BIGINT` | `BIGINT` | UNIQUE, NOT NULL | Unique numeric artwork ID on Redbubble (e.g. `156782390`). Used for deduplication during synchronization. |
| `title` | `VARCHAR` | `VARCHAR(255)` | UNIQUE, NOT NULL | Design title (e.g. *"Cosmic Cat Embroidery"*). |
| `description` | `TEXT` | `TEXT` | NOT NULL | Full text description used on the card and in SEO tags. |
| `keywords` | `TEXT` | `TEXT` | NOT NULL | Comma-separated keyword list for search optimization. |
| `imageName` | `VARCHAR` | `VARCHAR(255)` | NULL | Image file name (hash or slug from the CDN). |
| `externalImageUrl` | `TEXT` | `TEXT` | NULL | Direct URL to a high-quality image preview on the Redbubble CDN. |
| `externalLink` | `TEXT` | `TEXT` | NULL | Direct link to the product page in the Redbubble shop. |
| `category` | `VARCHAR` | `VARCHAR(255)` | DEFAULT `'no_category'` | Product category (e.g. `t-shirts`, `stickers`, `posters`). |
| `collection` | `VARCHAR` | `VARCHAR(255)` | DEFAULT `'no_collection'` | Collection name (e.g. `Vintage Animals`, `Geometric Thread`). |
| `backgroundColor` | `VARCHAR` | `VARCHAR(255)` | DEFAULT `'#FFFFFF'` | Primary background color in HEX format. |
| `backgroundColors` | `TEXT` | `TEXT` | NULL | Additional color palette or list of available shades. |
| `shared` | `BOOLEAN` | `BOOLEAN` | DEFAULT `false` | Visibility/publication flag for the shared catalog. |
| `props` | `JSON` | `JSON` | NULL | Additional unstructured metadata (source, original URL, etc.). |
| `createdAt` | `TIMESTAMP WITH TIME ZONE` | `TIMESTAMP` | DEFAULT NOW | Date the artwork was added to the catalog. |
| `updatedAt` | `TIMESTAMP` | `TIMESTAMP` | NULL | Date of the last metadata update or synchronization. |

### 2.3 Row Level Security (PostgreSQL / Supabase)

In addition to the tables, `init/postgres_tables.sql` enables Row Level Security and creates four policies:

```sql
ALTER TABLE public.studio ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.designs ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Public Read Studio" ON public.studio FOR SELECT TO anon, authenticated USING (true);
CREATE POLICY "Public Read Designs" ON public.designs FOR SELECT TO anon, authenticated USING (true);

CREATE POLICY "Service Role Studio All" ON public.studio FOR ALL TO service_role USING (true) WITH CHECK (true);
CREATE POLICY "Service Role Designs All" ON public.designs FOR ALL TO service_role USING (true) WITH CHECK (true);
```

Consequences:

- The `anon` and `authenticated` Supabase roles can only **read** both tables — this is sufficient for the storefront.
- All writes (INSERT/UPDATE/DELETE, including the Redbubble sync upsert) must go through the **service role** key (`SUPABASE_SERVICE_ROLE_KEY`), which bypasses RLS. Attempts to write with the anon key fail with a row-level security policy violation.

## 3. Stored Functions and Procedures

For selecting random designs (e.g. for a promo block or dynamic recommendations), optimized database functions are provided in the init scripts.

### 3.1 PostgreSQL (`init/postgres_functions.sql`)

```sql
-- Select a single random design
CREATE OR REPLACE FUNCTION get_random_design()
RETURNS SETOF design
LANGUAGE SQL
AS $$
    SELECT * FROM designs
    ORDER BY random()
    LIMIT 1;
$$;

-- Select three random designs
CREATE OR REPLACE FUNCTION get_random_designs()
RETURNS SETOF designs
LANGUAGE SQL
AS $$
    SELECT * FROM designs
    ORDER BY random()
    LIMIT 3;
$$;
```

> Note: the first function is declared `RETURNS SETOF design` (singular) in the current `init/postgres_functions.sql`, while the table (and therefore its composite type) is named `designs`. Verify the script executes cleanly in your environment before relying on it.

### 3.2 MySQL (`init/mysql_functions.sql`)

```sql
DELIMITER $$

CREATE PROCEDURE get_random_design()
BEGIN
  SELECT * FROM designs
  ORDER BY RAND()
  LIMIT 1;
END $$

CREATE PROCEDURE get_random_designs()
BEGIN
  SELECT * FROM designs
  ORDER BY RAND()
  LIMIT 3;
END $$

DELIMITER ;
```

### 3.3 Current usage status

These functions are **not invoked by the application code**. `utils/database.ts` queries the `designs` table directly; for example, the featured-designs block on the home page (`app/page.tsx`) calls `fetchDesigns(1, "", "", 3)` and relies on the `createdAt DESC` ordering. The stored random-selection functions remain available for ad-hoc SQL and future use.

## 4. Database Abstraction Layer (`utils/database.ts`)

The `utils/database.ts` module isolates the rest of the codebase from low-level SQL queries and driver specifics. It is the only data-access facade used by the app.

### 4.1 Provider switching and connection management

- `getProvider()` — reads `DATABASE_PROVIDER` (defaults to `supabase`) and throws on unsupported values.
- `getSupabase()` — lazily creates a `@supabase/supabase-js` client. The key is resolved as `SUPABASE_SERVICE_ROLE_KEY || NEXT_PUBLIC_SUPABASE_ANON_KEY`; if `NEXT_PUBLIC_SUPABASE_URL` or the key is missing, it throws `Missing Supabase environment variables`. Using the service-role key server-side is what allows writes to pass RLS (see 2.3).
- `getMySQLPool()` — lazily creates a `mysql2/promise` pool cached on `globalThis` (so it survives module re-instantiation). It requires `MYSQL_HOST`, `MYSQL_USER`, `MYSQL_PASSWORD`, and `MYSQL_DATABASE` (otherwise it throws `Missing MySQL environment variables`); `MYSQL_PORT` is optional and defaults to `3306`. The pool is configured with:
  ```typescript
  globalForMySQL.mysqlPool = mysql.createPool({
      host: MYSQL_HOST,
      port: MYSQL_PORT ? Number(MYSQL_PORT) : 3306,
      user: MYSQL_USER,
      password: MYSQL_PASSWORD,
      database: MYSQL_DATABASE,
      waitForConnections: true,
      connectionLimit: 10,
      queueLimit: 0,
      dateStrings: true,
      ssl: process.env.NODE_ENV === "production" ? { rejectUnauthorized: true } : undefined,
  });
  ```
- `closeDatabaseConnections()` — gracefully ends the MySQL pool; called by `scripts/sync-redbubble.ts` after a CLI run.

### 4.2 `getSiteConfig(): Promise<SiteConfig>`

Fetches all rows from the `studio` table and assembles them into a typed `SiteConfig` object via `mapDataToConfig(props)`.

- **Supabase**:
  ```typescript
  const {data} = await supabaseClient.from("studio").select("*").returns<ConfigProp[]>();
  return mapDataToConfig(data || []);
  ```
- **MySQL**:
  ```typescript
  const [rows] = await pool.query<mysql.RowDataPacket[] & ConfigProp[]>("SELECT * FROM studio");
  return mapDataToConfig(rows);
  ```

`mapDataToConfig` (`lib/config.ts`) deep-clones the bundled `config/config.json` as the base configuration and then applies the `studio` rows on top of it: keys with dot notation are expanded into nested objects, and a blocklist (`__proto__`, `constructor`, `prototype`) protects against prototype pollution. Merge order: **file defaults first, `studio` table rows override them**.

### 4.3 `fetchDesigns(page, searchQuery, collection, itemsPerPage)`

Performs pagination and filtering of the catalog.

- **Parameters**:
  - `page: number` — 1-based page number; values below 1 are clamped to 1.
  - `searchQuery: string` — case-insensitive title search.
  - `collection: string` — exact collection-name filter.
  - `itemsPerPage: number` — page size (default 12); clamped to the 1–100 range.
- **Return value**:
  ```typescript
  Promise<{ designs: Design[]; total: number }>
  ```
- **Query logic**:
  - Supabase query builder: `.from("designs").select("*", { count: "exact" })`, optionally `.ilike("title", `%${searchQuery}%`)` and `.eq("collection", collection)`, then a deterministic `.order("createdAt", { ascending: false })` and `.range(start, end)`. On error it logs and returns `{ designs: [], total: 0 }`.
  - MySQL uses a parameterized query with a parallel count:
    ```sql
    SELECT * FROM designs WHERE 1 [AND title LIKE ?] [AND collection = ?]
    ORDER BY createdAt DESC LIMIT ? OFFSET ?
    SELECT COUNT(*) as total FROM designs WHERE 1 [AND title LIKE ?] [AND collection = ?]
    ```

### 4.4 `getDesignById(id: string)`

Fetches the details of one design plus up to 3 related works from the same collection.

- **Signature**:
  ```typescript
  Promise<{ design: Design; relatedDesigns: Design[] } | null>
  ```
- **Logic**:
  - Looks up the row by primary key `id`. If not found, returns `null`.
  - Using the found `collection`, it fetches related rows with `collection = target.collection AND id <> target.id LIMIT 3` (`.eq("collection", ...)` + `.neq("id", id)` + `.limit(3)` on Supabase).

### 4.5 `fetchCollections(): Promise<string[]>`

Returns the list of distinct collection names, excluding empty strings and the `no_collection` placeholder.

- **Supabase**:
  ```typescript
  const {data} = await supabaseClient
      .from("designs")
      .select("collection")
      .not("collection", "is", null)
      .neq("collection", "")
      .neq("collection", "no_collection");
  return Array.from(new Set(data.map(i => i.collection).filter(Boolean)));
  ```
- **MySQL**:
  ```typescript
  const [rows] = await pool.query(
      "SELECT DISTINCT collection FROM designs WHERE collection IS NOT NULL AND collection != '' AND collection != 'no_collection' ORDER BY collection ASC",
  );
  return rows.map(r => r.collection);
  ```
  On a Supabase error the function logs and returns `[]`.

## 5. Step-by-Step Initialization and Migration Instructions

### 5.1 Initializing in Supabase (PostgreSQL)

#### Option 1: Via the web interface (Supabase Dashboard)
1. Sign in to the [Supabase](https://supabase.com/dashboard) dashboard and open your project.
2. Open **SQL Editor** in the left menu.
3. Create a **New Query**, paste the contents of `init/postgres_tables.sql`, and press **Run**.
4. Create a second query with the contents of `init/postgres_functions.sql` and run it.
5. Verify the tables (and their RLS policies) in **Table Editor**.

#### Option 2: Via `psql` with the project connection string
Use the connection string from **Project Settings → Database** in the Supabase dashboard:
```bash
psql "postgresql://postgres:[YOUR-PASSWORD]@db.[PROJECT-REF].supabase.co:5432/postgres" \
  -f init/postgres_tables.sql
psql "postgresql://postgres:[YOUR-PASSWORD]@db.[PROJECT-REF].supabase.co:5432/postgres" \
  -f init/postgres_functions.sql
```

### 5.2 Initializing in MySQL

1. Connect to the MySQL server via the console client or a GUI tool (DataGrip, DBeaver, MySQL Workbench):
   ```bash
   mysql -h your_mysql_host -u your_user -p
   ```
2. Create the database (if it does not exist yet) and switch to it:
   ```sql
   CREATE DATABASE design_studio CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
   USE design_studio;
   ```
3. Apply the table and procedure files:
   ```bash
   mysql -h your_mysql_host -u your_user -p design_studio < init/mysql_tables.sql
   mysql -h your_mysql_host -u your_user -p design_studio < init/mysql_functions.sql
   ```

### 5.3 Seeding the `studio` table

For the initial shop setup, insert the base parameters into `studio`.

PostgreSQL:
```sql
INSERT INTO studio (key, value) VALUES
('name', 'Design Studio Pro'),
('intro', 'Exclusive Art & Print Studio'),
('domain', 'studio.example.com'),
('email', 'contact@example.com'),
('representation.redbubbleShopUrl', 'https://www.redbubble.com/people/your-shop/shop'),
('social.twitter', 'https://x.com/your-shop'),
('social.instagram', 'https://instagram.com/your-shop');
```

MySQL (`key` is a reserved word and must be backtick-quoted):
```sql
INSERT INTO studio (`key`, value) VALUES
('name', 'Design Studio Pro'),
('intro', 'Exclusive Art & Print Studio'),
('domain', 'studio.example.com'),
('email', 'contact@example.com'),
('representation.redbubbleShopUrl', 'https://www.redbubble.com/people/your-shop/shop'),
('social.twitter', 'https://x.com/your-shop'),
('social.instagram', 'https://instagram.com/your-shop');
```

If a key is absent from the table, the matching default from `config/config.json` is used (see 4.2), so seeding every key is optional.
