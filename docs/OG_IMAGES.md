# Горизонтальные карточки Facebook и Twitter

Аплоудер заранее собирает один JPEG 1200 × 630 на принт и загружает его в
существующий R2. Design Studio хранит постоянное назначение и отдаёт готовые
байты либо воспроизводит тот же макет. Публикации постов в соцсети нет.

## Оформление и контракт

Выбраны варианты 1/2/3/5: `editorial`, `diagonal`, `collage`, `color-fields`.
В диагональном варианте фотография целиком размещается левее x=500,
диагональная плашка начинается не левее x=505. Коллаж использует футболку,
кепку и кружку, заголовок белый. Без подтверждённых дополнительных товаров
доступны остальные три композиции. Цвет товаров и рисунок не меняются.

Семь палитр: terracotta, graphite, navy, forest, burgundy, plum, ochre.
Макет и цвет выбираются независимо по постоянному UUID. Это 28 возможных
сочетаний; сохраняется один результат. Полное название укладывается по
метрикам шрифта, без многоточий. Если оно не помещается при читаемом размере,
назначение не записывается. JPEG не превышает 1 MiB.

`@pod/og-renderer@1.0.0` находится в pod-uploader/packages/og-renderer.
Сайт устанавливает зафиксированный `vendor/pod-og-renderer-1.0.0.tgz`.
Сеть и БД вне генератора. В архив включены Inter, Noto Serif и Poppins,
их лицензии OFL; Next tracing включает шрифты в оба товарных маршрута.
После выпуска нельзя менять v1: будущий рендер должен сохранять старые версии.

`designs.ogImage` — nullable JSONB/JSON, отдельно от `cdnImage` и
`pinterestImage`. Миграция 010 добавляет колонку и атомарный PostgreSQL RPC;
MySQL использует транзакцию с блокировкой строки. Все обращения через
utils/database.ts. Скрейперы и импорт листингов не записывают это поле.

- `assignment`: версии, UUID, шаблон, палитра и конкретные цвета, снимки
  полного названия, категории и подписи, строки/размеры текста, URL/SHA-256/crop
  исходников, канонический SHA-256 назначения.
- `asset`: null либо ключ, SHA-256, размеры и количество байт JPEG.

GET/PUT `/api/v1/designs/og-image` авторизованы `LISTINGS_API_TOKEN`.
GET читает активный каталог постранично или ищет по UUID/SHA-256/sourceImageId/
Redbubble ID; противоречивые идентификаторы дают 409. PUT assign закрепляет
первое назначение; идентичный повтор успешен, замена даёт 409 с сохранённым
значением. PUT ready принимает только файл того же назначения. RPC доступен
только service_role. Название, новые товары и обновления генератора не
переназначают уже выбранное оформление.

## Выдача сайта

Сохраняются `/designs/<slug>/opengraph-image` и `/twitter-image`.
Оба используют одну функцию. Для назначенных карточек metadata страницы
явно задаёт JPEG 1200 × 630 и URL с `?v=<assignment-hash>`; постороннее
изменение `updatedAt` не меняет адрес картинки. Конфигурация PNG в файловой
конвенции остаётся для прежних карточек без назначения; явная metadata
назначенной карточки имеет JPEG и заменяет её автоматически полученный URL.

Сначала проверяется активность принта. Неизвестный/неактивный — 404/no-store.
Облачный файл скачивается с таймаутом 3 секунды, проверяется размер, формат,
полное декодирование и SHA-256. Ответ — JPEG через адрес сайта, кеш браузера
86400 секунд, shared-кеш 604800 секунд. Прокси позволяет сохранить прозрачный
fallback по тому же адресу; за это сайт расходует запросы и трафик.

При ошибке CDN те же исходники Redbubble скачиваются с ограничением размера
и таймаутом, проверяются по сохранённому SHA-256 и рендерятся тем же пакетом.
Кеш резервного ответа — 60 секунд. Одновременный отказ CDN и исходников даёт
503/no-store. Гарантируются сохранённые композиция, цвета и текст; побайтовое
совпадение зависит от доступности тех же исходных байтов и версии генератора.
Без назначения остаётся прежний PNG-рендер. Общая брендовая OG-карточка не меняется.

разрешённого выпуска необходимо импортировать в БД эти назначения, проверив
хеши и атомарный ответ сервера. Нельзя заново выбирать оформление для уже
подготовленных файлов по изменившимся данным. Локальная резервная копия:

никаких автономных запусков нет. Cron и задания планировщика не создаются.

выдачу сохранённых макетов. Старый код сайта будет выдавать старую OG-карточку.

## Лимит Image Optimization Vercel

Готовые облачные мокапы и OG/Pinterest JPEG не проходят через `/_next/image`.
Дополнительные мокапы Redbubble, переданные в DesignImage через `src`, также
загружаются напрямую (`unoptimized`); lazy loading, размеры и watermark
сохраняются. Это исключает их из счётчика Vercel Transformations. Основное
удалённое изображение для принтов без облачного мокапа пока сохраняет прежний
оптимизатор. Общий расход команды Vercel зависит и от остальных проектов.
