# threadquirk.lv — аудит поиска принтов и органической видимости

Дата: 10 октября 2026 года. Основание: две основные цели из `AGENTS.md` — качественные принты, которые легко найти, и максимальная полезная органическая видимость при минимальных расходах.

## Вывод

Сайт уже имеет рабочую техническую основу для поиска: серверный каталог, читаемые адреса принтов, canonical, sitemap, разрешённый обход и структурированные данные. Главные подтверждённые ограничения — поиск только по заголовкам, неполное покрытие коллекциями и слабое представление тематических страниц. На телефоне каталог неудобен для быстрого сравнения вариантов.

Сначала нужно улучшить обнаружение уже существующих принтов. Платный поисковый сервис, массовая генерация SEO-текстов и увеличение каталога сами по себе эти проблемы не решают. Предлагаемый первый этап использует существующие Next.js, базу данных, конфигурацию и бесплатные инструменты поисковиков.

## Область проверки и ограничения

- Живые страницы: главная, каталог, коллекции Photography и Everyday Dev Humor, пустой результат поиска, карточка Cached Cat; карточка и каталог проверены на компьютере и телефоне. Размеры для адаптивной проверки: 1440×900 и 390×844.
- HTTP: robots, sitemap, каталог, страница 2, коллекция, поиск, пять карточек из разных частей sitemap, несуществующая карточка, Pinterest landing page, About, HTTP/www-перенаправления и один оптимизированный файл изображения.
- Публичный каталог выгружен целиком: 284 записи, по 50 за запрос. Проверены результаты всех 24 фильтров коллекций, включая вторую страницу большой коллекции.
- Код: страницы каталога/принтов/главной, компоненты поиска, карточек, навигации, карусели, аналитики; фасад БД, image helper, публичный DTO, robots, sitemap и метаданные.
- Подтверждённый владельцем рынок: международная англоязычная аудитория. Поиск, тексты и тематические посадочные страницы ориентировать на её задачи; многоязычность не является приоритетом первого этапа.
- Search Console, Bing Webmaster Tools, GA4 и журналы production не были доступны в этом аудите. Нельзя утверждать количество проиндексированных страниц, объём трафика, причины исключения из индекса или поисковую частотность тем.
- Поисковый инструмент не вернул результатов на `site:threadquirk.lv`. Это сигнал для дополнительной проверки, а не доказательство отсутствия индексации. Google прямо описывает ограничения [оператора site:](https://developers.google.com/search/docs/monitor-debug/search-operators/all-search-site).
- PageSpeed API вернул HTTP 429 из-за квоты. LCP, INP, CLS и Lighthouse score не измерены. Время отдельных HTTP-запросов не используется как замена Core Web Vitals.
- Качество физических отпечатков, исходных файлов и всех 284 иллюстраций не проверено. Мокап не доказывает качество печати. Замечания относятся к обнаружению, представлению и содержимому каталога.
- Код приложения, production-конфигурация и данные БД не менялись. Сохранены только отчёт и локальные снимки публичных данных в `.cache/threadquirk-audit/`.

## Подтверждённые проблемы и бесплатные исправления

### 1. Поиск теряет релевантные принты — высокий приоритет, UX

**Доказательство:** [поиск `cat lover gift`](https://threadquirk.lv/designs?search=cat+lover+gift) возвращает 0 результатов. При этом [публичный API с фильтром keywords](https://threadquirk.lv/api/v1/prints?keywords=cat+lover+gift&limit=50) возвращает 8 принтов. Обычный API-поиск `q=cat+lover+gift` также возвращает 0. Это не отсутствие товара: нужные данные уже существуют.

**Причина в коде:** `utils/database.ts:181`, `:198`, `:247` проверяют только `title` через поиск подстроки. `:189`, `:204`, `:270` сортируют по дате создания. Слова запроса должны идти подряд; перестановки слов и слова только из тегов не учитываются. Интерфейс не использует уже существующие keywords для обычного поиска.

**Влияние:** посетитель получает ложный сигнал «подходящих принтов нет». Внешнее SEO не компенсирует плохой поиск после входа на сайт.

**Исправление:** сначала поиск по title + keywords + description, разбиение на слова, нормализация регистра и пробелов. Все значимые слова запроса должны находиться в этих полях; точный заголовок и совпадения в заголовке получают больший вес. Для запроса сортировать по релевантности, для обычного просмотра сохранить порядок новых работ. Реализовать одинаковое поведение Supabase/MySQL через фасад. Не загружать весь каталог в браузер. Синонимы и опечатки добавлять только по наблюдаемым провалам, без платных векторных сервисов.

**Проверка:** все 8 принтов с точным тегом `cat lover gift` присутствуют среди результатов; перестановка слов не обнуляет выдачу; составить 15–20 реальных поисковых сценариев с ожидаемыми принтами в первых пяти результатах. Сохранить корректную пагинацию и `noindex` поисковых страниц.

### 2. 107 принтов не покрыты коллекциями — высокий приоритет, UX и внутренние связи

**Доказательство:** 107/284 записей (37,7%) имеют пустую основную коллекцию и не обнаружены ни в одном из 24 публичных фильтров коллекций. Проверены также дополнительные членства, которые реально возвращает фильтр; проблема не сведена к одному полю DTO.

**Влияние:** при выборе темы посетитель исключает больше трети каталога. Эти карточки также не получают тематические переходы и связанные принты по текущей реализации.

**Исправление:** подготовить список этих 107 работ и назначить релевантные коллекции. Перед изменением данных сверить источник: отсутствие членства может происходить в исходном магазине либо при синхронизации; аудит не установил причину. Если членство есть в источнике, исправить sync. Если его нет, организовать работы в источнике и синхронизировать. Не править производные связи вручную так, чтобы следующая синхронизация их затёрла.

**Проверка:** каждый принт, подходящий существующей тематике, появляется в соответствующем фильтре; список оправданно неклассифицированных работ явно определён. Контроль до/после по числу принтов без членства и по ручной проверке релевантности.

### 3. Коллекции плохо оформлены как поисковые посадочные страницы — высокий приоритет, SEO

**Доказательство:** [Photography collection](https://threadquirk.lv/designs?collection=Photo%20and%20Video%20lover) содержит 29 работ, но title = `Our Designs - ThreadQuirk`, H1 = `Our Designs`, описание — общий текст о числе принтов и всех 24 коллекциях. Everyday Dev Humor имеет такие же title и H1. Ни одной коллекции нет в sitemap. Основной доступ к полному перечню — select, а не отдельный блок обычных ссылок.

**Причина:** `app/designs/page.tsx:36`, `:38`, `:104`; `app/sitemap.xml/route.ts:43`, `:89`. Описания коллекций уже доступны в БД через `fetchFeedCollections`, но каталог их не показывает.

**Влияние:** тематическая страница слабо объясняет, какую задачу она решает; нет удобного входа «футболки для фотографов» или «юмор для программистов». Одинаковые заголовки не означают автоматическую SEO-санкцию, но дают мало контекста посетителю и поисковику.

**Исправление:** начать с 3–5 наполненных тем: Programming (22 результата), Photography (29), Food (20), Pet lovers (7), Open Source (40). Выбор уточнить по Search Console и реальным запросам; эти количества не являются оценкой спроса. Для каждой — понятные title/H1, полезное короткое введение, релевантный каталог и ссылки на соседние темы. Добавить обычные ссылки с главной/каталога и canonical URL выбранных страниц в sitemap.

**Простое первое решение:** улучшить существующие `/designs?collection=...`; параметры URL сами по себе не препятствуют индексации. Отдельные `/collections/<slug>` имеют смысл позже, если помогают архитектуре. Изменение адресов не должно подменять работу над содержанием. Сохранить отдельные canonical пагинации. Произвольные поисковые комбинации оставить `noindex`; не добавлять их в sitemap.

**Проверка:** выбранные темы имеют разные содержательные title/H1/description, уникальное полезное содержание, 200 и self-canonical, доступны обычными ссылками максимум за два перехода от главной и включены в sitemap. Далее проверка выбранных URL в Search Console, показы и переходы по соответствующим темам.

### 4. Главная не помогает сразу выбрать принт — высокий приоритет, UX и содержание

**Доказательство:** [главная](https://threadquirk.lv/) использует `Innovative Design Studio`, `Weaving innovation into every design`, общий промослайдер и не содержит поиска. На 390×844 блок реальных работ начинается ниже первого экрана. Метаданные описывают дизайн-студию и «thread-based designs», а не понятный каталог принтов. В `app/page.tsx:67` Featured Designs — просто пять самых новых работ.

**Влияние:** посетитель должен сначала понять назначение сайта и перейти в общий каталог; новые работы одной тематики вытесняют разнообразие. Отбор по дате не является отбором лучших принтов.

**Исправление:** первый экран — конкретное предложение, поиск и 4–6 видимых тематических ссылок, иллюстрации реальных принтов. Сократить промоблок. Например, формулировка про оригинальные принты и подарки для программистов, фотографов и любителей животных, если она соответствует выбранному рынку. Изменять брендовые тексты через конфигурацию. Отдельно подобрать небольшой список лучших/представительных работ; достаточно конфигурации, новая админка не нужна.

**Проверка:** поиск и входы в темы видны на первом экране 390×844; на тестовых сценариях посетитель за ≤30 секунд открывает подходящий принт. Это целевой критерий, а не измеренный текущий результат.

### 5. Мобильный каталог затрудняет сравнение — высокий приоритет, UX

**Доказательство:** на 390×844 изображение первой карточки занимает примерно 343×457 CSS px; её заголовок начинается около y=807. На экран помещается практически один вариант. Далее следуют описание, коллекция и повторная ссылка. В каталоге 19 страниц по 15 работ. В выбранной карточке первый Buy на мобильном расположен около y=1069, после изображения, длинного заголовка и описания.

**Причина:** сетка с одной колонкой до 640px (`app/designs/page.tsx:121`), портретная карточка и подробный текст (`app/components/DesignCard.tsx:26`, `:49`). На detail есть `min-h-[200px]` у описания (`app/designs/[slug]/page.tsx:187`), дающий лишнее пространство при коротком тексте.

**Исправление:** проверить компактную мобильную сетку из двух карточек, короткий отображаемый заголовок и перенос описания на detail; сохранять читаемость принта, особенно типографического. При необходимости уменьшать карточку только после проверки фактических мокапов. На detail поднять действия ближе к заголовку и убрать искусственный минимум высоты описания. Полное изображение и описание должны оставаться доступными. Не вводить бесконечную прокрутку ради этой задачи.

**Проверка:** на 390px можно сравнить два варианта рядом без горизонтальной прокрутки, названия читаются, карточки доступны клавиатурой; возвращение из detail сохраняет поиск/фильтр и позицию. Сравнить время выбора на одинаковых сценариях с текущим вариантом.

### 6. Поиск не показывает состояние выполнения и оставляет слабый выход из пустой выдачи — средний приоритет, UX

**Доказательство:** `CatalogSearchBar.tsx:21` отбрасывает `isPending` из `useTransition`; нет сообщения об обновлении результатов. При нуле результатов доступны только текст и общий сброс. Сброс активных фильтров показан только при пустой выдаче (`app/designs/page.tsx:134`).

**Исправление:** показать «Searching…»/состояние обновления, видимые активные фильтры со сбросом каждого; при нуле — тематические ссылки или осмысленное ослабление запроса после улучшения поиска. Не подмешивать нерелевантные результаты без объяснения.

**Проверка:** на замедленном соединении видно, что выдача обновляется; можно снять коллекцию без потери поискового текста и убрать запрос без потери коллекции.

### 7. Не хватает измерений успешного поиска — средний приоритет, при этом настройка нужна в начале

**Доказательство:** собственное событие в коде — `buy_click`; Search Console linking описан в `docs/ANALYTICS.md`, но его production-настройка не проверена. У поиска нет собственных событий с числом результатов. Автоматический `view_search_results` может зависеть от GA4 Enhanced Measurement; его наличие в аккаунте не установлено.

**Исправление:** проверить уже существующие Google Search Console/Bing Webmaster Tools и GA4, отправить sitemap, снять исходные показатели. Если аккаунты не настроены — использовать бесплатные инструменты. Зафиксировать результат поиска (число найденных работ), выбор карточки и `buy_click` без дублирования автоматических событий, с существующим согласием на аналитику. Не передавать произвольные поисковые строки, содержащие личные данные.

**Проверка:** сохранён baseline за последние 28 дней при наличии данных; известны статусы главной, каталога и 5–10 принтов через URL Inspection. События проверены в DebugView и не отправляются после отказа от аналитики. Поведенческие измерения учитывают, что посетители без согласия не попадают в GA4.

### 8. Содержание нуждается в редактуре и проверке достоверности — средний приоритет, качество и SEO

**Доказательство:** в описании `I Came I Saw I Auto-Focused Camera Shirt` есть `out ther.`. Названия коллекций неоднородны и местами неестественны: `Photo and Video lover`, `For gourmets and food lovers`. About повторяет текст из конфигурации по умолчанию: основание в 2024 году и «талантливая команда». Подтверждения этих утверждений в доступных материалах нет; это не доказательство их ложности.

**Исправление:** отредактировать реальные ошибки, названия и короткие видимые подписи. Проверить About с владельцем и оставить конкретные достоверные сведения об авторе, работах и процессе. Для 20–30 выбранных принтов уточнить сюжет, надпись, кому подходит и какие товары действительно доступны. Не выдумывать качество ткани, отзывы, продажи или свойства печати. Изменения данных согласовать с источником sync, чтобы они сохранялись.

**Проверка:** ручная редакторская проверка выбранных работ и About; информация соответствует изображению и маркетплейсам. Критерий качества — полезность выбора, а не длина текста. Основа SEO — [полезное содержание для людей](https://developers.google.com/search/docs/fundamentals/creating-helpful-content).

### 9. Сопутствующие принты учитывают только основную коллекцию — средний приоритет, UX

**Доказательство:** `utils/database.ts:327`, `:347`, `:373` — связанные работы запрашиваются по одному legacy-полю collection, тогда как основной фильтр поддерживает many-to-many. Например, Programming через фильтр содержит 22 работы, а основной collection указан лишь у 2. Для 107 работ с пустым collection связанные работы вообще не запрашиваются.

**Исправление:** после восстановления коллекций выбирать связанные работы по реальным членствам, исключая текущую карточку; при необходимости использовать совпадения проверенных тегов. Сохранить одинаковое поведение провайдеров и ограничение числа карточек. Не добавлять платный рекомендательный сервис.

**Проверка:** у работ с дополнительным членством появляются соответствующие рекомендации; раздел не предлагает принты из чужой темы и не повторяет текущий.

### 10. 60 публичных карточек не имеют imageUrl — дополнительный приоритет, бесплатное распространение

**Доказательство:** 60/284 ответов публичного API имеют пустой `imageUrl`, при этом все имеют `mockupUrl`. `lib/public-api.ts:54` передаёт исходный URL без fallback. Сам storefront использует mockup и от этого не теряет изображения.

**Влияние:** внешние блоки, которые используют только `imageUrl`, могут показывать пустые изображения. Это ограничивает уже предусмотренную бесплатную дистрибуцию каталога через собственные сайты/виджеты. Прямой ущерб ранжированию основного сайта не установлен.

**Исправление:** определить и документировать fallback для потребителей (`mockupUrl || imageUrl`) либо восстановить исходные изображения, если они обязаны быть в DTO. Не менять смысл artwork-поля молча. Проверить реальные потребители перед изменением API.

**Проверка:** в тестовом внешнем блоке все 284 работы отображают изображение; публичный контракт и фоновый override сохраняют смысл.

## Приоритетный план

Оценки ниже — ориентир объёма труда, а не обещание сроков. Новых платных сервисов план не требует; используются текущий хостинг и БД. Бесплатное ПО не исключает затрат времени и расходования существующих лимитов.

**Практический первый цикл:** начать с P0-A и P0-B, затем P1-A/P1-B. P1-C/P1-D следуют за ними. Не запускать все изменения одновременно: фиксировать дату каждого этапа, чтобы понимать результат.

Начальные темы — гипотезы на основе наполненности каталога, не готовое семантическое ядро. Следующий шаг — исследовать англоязычные запросы и результаты Google/Bing для международной аудитории. Примеры кандидатов: `funny programmer shirts`, `photography t-shirts`, `cat lover gifts`; спрос и подходящий формат страниц ещё не проверены. Страны для первых проверок выбирать по данным Search Console, а при отсутствии данных — явно обозначить их как эксперимент. Не создавать страницы под каждый тег и каждую комбинацию фильтров.

## Метрики двух целей

1. **Поиск принтов:** доля запросов с нулевой выдачей; попадание ожидаемого принта в top-5 контрольных сценариев; время до открытия подходящей карточки; переход из результатов в карточку; доля работ без тематического членства.
2. **Органика:** индексируемые/проиндексированные важные URL по инструментам поисковиков; показы и клики по небрендовым запросам; органические входы на коллекции и принты; последующие `buy_click` у согласившихся на аналитику посетителей.
3. **Качество:** редакторская проверка выбранных работ, читаемость надписей на реальных мокапах и соответствие описания дизайну. Качество физических отпечатков требует отдельной проверки; не подменять его числом карточек или посещений.

Повторная оценка: после первого переобхода проверить URL; через 4–6 недель сравнить показатели с baseline с учётом низкого трафика, сезонности и даты публикации. Это рабочий интервал наблюдения, не гарантия роста или срока индексации.

## Что сейчас не оправдано

- Платные Algolia, векторный поиск, платная SEO-подписка или новая инфраструктура для каталога из 284 работ: начинать с имеющихся данных и простого поиска.
- Массовый SEO-блог, автоматический перевод всех страниц и страницы для каждого тега: сначала полезные англоязычные коллекции и проверка спроса международной аудитории.
- Переписывание всего frontend, новая админка, checkout, миграция БД или домена: подтверждённых оснований в этом аудите нет.
- Выдуманные Product offers/цены/рейтинги ради rich results. Уже есть CreativeWork и BreadcrumbList; [Google требует реальные offers/review/aggregateRating для Product snippets](https://developers.google.com/search/docs/appearance/structured-data/product-snippet).
- Попытки «починить индексацию», открыв внутренний поиск или Pinterest `/p` для индекса: их текущая политика осмысленна.
- Покупка ссылок. Сначала релевантные ссылки из собственных профилей/проектов и полезные материалы; Pinterest — отдельный канал referral, его нельзя автоматически считать Google/Bing organic.

Для будущего IndexNow ориентироваться на [официальный протокол](https://www.indexnow.org/documentation): отправлять действительно новые/изменённые/удалённые canonical URL. Это уведомление участвующих поисковиков, а не гарантия индексации и не замена Google sitemap.

Владелец выбрал международную англоязычную аудиторию. Национальные домены дают [географический сигнал](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites); для `.lv` это нужно учитывать при анализе показов по странам. Это не запрет международного продвижения и не повод сейчас тратить деньги на смену домена.
